# 底座变更记录

记录「阅读（Legado）」底座在这里被换过几回、为什么换、换了之后哪些地方要跟着改。

## 时间线

| 日期 | 变更 | 原因 |
|---|---|---|
| 2026-11-05 | 以 `base.apk(6).1`（Legado 3.23.051323）拆包做静态分析与 smali 层实验 | 早期探路，产物在 `reader-merge-20261105` |
| 2026-11-11 | 正式工程改用**源码构建**，锁定 `3.26.23` | 拆包改 smali 只能打补丁，做不了持续迭代 |
| 2026-11-11 | 上游 `gedoor/legado` 改为 `HapeLee/legado-with-MD3` | **见下** |

## 为什么换镜像

`gedoor/legado` 在 **2026-05-27** 被清空成一个公告仓库：

- 整个仓库只剩 `README.md`（707 字节）和 `公告链接.png`
- **没有源码、没有 tag、没有历史**，`git ls-remote` 只能看到一个 `main` 分支的一个提交
- 公告原文写明「删除项目内容」，并链到阅文的知识产权保护公告

所以 `git clone --branch 3.26.23` 必然报 `Remote branch 3.26.23 not found`。

现行来源：

```json
// gradle/base-source.json
{
  "repo": "https://github.com/HapeLee/legado-with-MD3.git",
  "ref": "3.26.23"
}
```

`HapeLee/legado-with-MD3` 保留完整 tag 历史（3.26.2 → 3.26.25），
其中 `3.26.23` = `35d013a0`，与上游发布版同源。它在上游基础上做了 Material Design 3 重构，
本仓库做的「番茄排版 + 旷野书源 + AI 纠错」这套改动与 MD3 重构不冲突。

## 底座自身的现状（3.26.23 + MD3）

换上去之后发现几处与「经典 Legado」不同，构建脚本都按实际对齐了：

| 项 | 底座实际 | 影响 |
|---|---|---|
| 包名 | `io.legato.kazusa`（不是 `io.legado.app.release`） | **与 4.00.x 老包不是同一个应用**，不能覆盖升级 |
| 版本号来源 | `app/version.properties`（VERSION_MAJOR/MINOR/PATCH） | 改 `build.gradle.kts` 没用，要改 properties |
| versionCode | `System.getenv("COMMIT_NUMBER")` 优先，否则 32640 | CI 要显式给，否则版本号不递增 |
| versionName | `System.getenv("APP_VERSION_NAME")` 优先 | CI 用 `-P` 或 env 注入 |
| 构建任务名 | `appCoreRelease` / `appComicRelease`（flavor = mode × engine） | 没有 `appRelease`，直接跑会 ambiguous |
| 签名 | `hasProperty("RELEASE_STORE_FILE")` 才建 signingConfig | 要用 `-PRELEASE_STORE_FILE=...`，环境变量无效 |
| compileSdk | 37（Compose 1.13.0-beta01 的 AAR 元数据要求 ≥ 37.1） | 镜像得带 android-37 |
| Java 版本 | sourceCompatibility 21 | JDK 17 构建会失败，需要 21 |
| ABI 拆分 | `splits.abi` 默认开启，`isUniversalApk = true` | 产物按 ABI 分开，收集器要认文件名 |

## 包名与老用户的关系

| 版本 | 包名 | 能否互相覆盖 |
|---|---|---|
| 3.99.x / 4.00.x（拆包改 smali 那一批） | `io.legado.app.release` | 可以互相覆盖 |
| 4.1.0 起（源码构建） | `io.legato.kazusa` | **不能**，是另一个应用 |

两条路可选：

1. **保持 `io.legato.kazusa`**：当作新应用发，老用户手动导出/导入书源与书架；
2. **把 applicationId 改回 `io.legado.app.release`**：能覆盖老包，但要同时确认签名密钥一致，
   且上架/分发时容易被认成同一应用。

这件事必须在 4.2.0 之前定下来，`docs/令牌权限清单.md` 里的发版说明也要跟着改。

## 首发实测记录（v4.1.0，2026-11-11）

流水线从 0 到跑通一共踩了 7 个坑，逐个记下来省得再犯：

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | `Failed to find package 'tools'` | `android-actions/setup-android@v3` 在 ubuntu-26.04 上装 `sdkmanager tools`，该包已被 Google 下架 | 不再用这个 action，直接吃镜像自带的 ANDROID_HOME |
| 2 | `Remote branch 3.26.23 not found` | `gedoor/legado` 已清空 | 换 `HapeLee/legado-with-MD3` |
| 3 | `ANDROID_HOME` 为空 | `actions/setup-java` 会把它置空 | 自行探测 `/usr/local/lib/android/sdk` 并写回 `GITHUB_ENV` |
| 4 | `app/build.gradle.kts ENOENT` | 底座在 `build/base/legado/`，不在仓库根 | `bump-version.js` 改候选路径；底座版本号交给 `patch-base-version.js` |
| 5 | `Task 'assembleAppRelease' is ambiguous` | flavor = mode(app/core) × engine(core/comic)，共 6 个候选 | 明确用 `assembleAppCoreRelease` |
| 6 | `Configuration cache state could not be cached: LintTool_Decorated` | AGP lint 任务与 Gradle 9.8 配置缓存序列化不兼容 | CI 加 `--no-configuration-cache` |
| 7 | 附件名变成 `-.-arm64-4.1.0.apk` | GitHub 对附件文件名和显示名都做 ASCII 清洗，中文字符被剥掉且不回填 | 附件用 `reader-fanqie-<abi>-<ver>.apk`，Release 正文给中文对照表 |

另外两个需要在 4.2.0 修掉的设计问题：

- `versionCode` 目前是 `max(32640, MA*10000+MI*100+PA)` = **32640**，因为 4.1.0 → 40100 已经超过它，
  但 4.0.0 的算法是 `major*10000+minor*100+patch`，两套算法混用会让 versionCode 忽大忽小。
  **4.2.0 起统一为 `major*10000 + minor*100 + patch`**，即 4.2.0 → 40200。
- 底座 `compileSdk = 37`、`JavaVersion 21`，CI 的 JDK 17 之所以能过是因为 Gradle Toolchain 自动下载了 21；
  显式写 `java-version: '21'` 更快。
